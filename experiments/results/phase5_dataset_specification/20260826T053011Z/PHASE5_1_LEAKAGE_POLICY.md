# Phase 5.1 — Leakage Policy

One rule per leakage vector, each traced to the code/evidence that makes it
concrete rather than abstract.

## 1. Timestamps

**Rule**: a pre-decision input field (`observations`, `workload`,
`agent_output.samples` up to the decision point) may carry only records
whose `Availability` is `AVAILABLE_BEFORE_DECISION` or
`AVAILABLE_AT_DECISION`. This is enforced today by
`ensure_decision_snapshot()` in `architecture.py`, which raises
`TIMESTAMP_VIOLATION` for anything else — the dataset schema's
`temporal.availability_of_this_record` field exists precisely so a
downstream consumer can replicate that same check without re-running the
pipeline. `DecisionTimeContract.validate()`'s ordering invariant
(`snapshot <= generated <= decision`) must hold for every episode retained
in the dataset; an episode that violates it is a data-quality defect, not
a record to silently drop — it must be flagged `evidence_class=8` and
excluded from any benchmark view, with the violation itself preserved as
an audit trail entry.

## 2. Run IDs

**Rule**: `run_id` may appear as an identity field everywhere, but must
never be used as a memory-retrieval scope key, and diagnosis evidence
eligibility must be restricted to the current `run_id`
(`DiagnosisEngine._eligible_current_incident`, the fix for
`EVALUATION_INCIDENT_001`). A dataset consumer replaying diagnosis evidence
from this dataset must filter by `run_id` before considering any event
"current," exactly as the fixed code does — the schema's
`memory_interaction.scope_key` field documents `(workload_id,
environment_id, failure_class)` as the only legal scope, `run_id` excluded
by construction (`source_run_id != exclude_run_id` in `memory.py`).

## 3. Workload IDs

**Rule**: see `PHASE5_1_SPLIT_POLICY.md` §2 — `workload_id` is the
mandatory grouping key for sample-level splits. Separately, a
`workload_id`'s scenario-generating distribution is environment-specific
(`scenario_fn` differs per `EnvironmentProfile`); a `workload_id` must
never be treated as if it could have been generated by a different
environment than the one recorded in `identity.environment_id`.

## 4. Environment IDs

**Rule**: any model, threshold, or feature choice fit using records from a
non-`development`-role environment (`held_out` or `robustness`) is a
leakage violation of the exact kind Phase 4.9/post-P5 Step 4 were designed
to prevent. The schema's `generalization.zero_shot` boolean exists so a
benchmark harness can assert this was true before reporting a
generalization number; a value of `false` must be treated as
disqualifying for any "generalization" claim (though the record remains
valid for a same-environment in-distribution evaluation).

## 5. Repeated incidents

**Rule**: see split policy §2 (grouping by `workload_id`). Additionally,
for the memory/adaptation benchmark view specifically (see
`PHASE5_1_BENCHMARK_VIEWS.md`), a repeated-incident sequence (same
`workload_id`, multiple `run_id`s) must be evaluated in strict temporal
order — a consumer must never expose a later `run_id`'s memory write to an
earlier `run_id`'s decision. This is already enforced by
`FailureMemoryStore.retrieve`'s `at_or_before` boundary; the dataset must
preserve `recorded_at` faithfully enough (never approximated forward) that
a downstream replay cannot accidentally invert this order.

## 6. Failure labels

**Rule**: `failure.failure_class` and `failure.failure_detected` are
`DERIVED_LABEL`s computed deterministically from raw `failure_detected`/
`failure_classified` events at generation time — they are eligible as
labels. They must never be back-filled using information from a
`diagnosis` record (which is a `MODEL_DIAGNOSIS`, not ground truth) or a
future episode's memory record.

## 7. Diagnosis outputs

**Rule**: `diagnosis.suspected_cause` and `diagnosis.confidence` are
permanently `label_type = MODEL_DIAGNOSIS`. No transformation, however
indirect, may promote a diagnosis output into a `ground_truth` or
`OBSERVED_OUTCOME_VALIDATED` field anywhere downstream, including inside
`MemoryRecord.root_cause` (which is itself sourced from a diagnosis and
therefore also carries `MODEL_DIAGNOSIS` provenance when traced back,
regardless of how confidently it reads in the store).

## 8. Recovery outcomes

**Rule**: only `SignalRecoveryValidator`'s independently re-derived
`ValidationOutcome.status` is eligible as `OBSERVED_OUTCOME_VALIDATED`.
`Recovery.executor_self_report` is retained (for discrepancy analysis, per
provenance contract §3) but is always `label_type =
EXECUTOR_SELF_REPORT_UNVALIDATED` and must never substitute for
`validation.validation_status` in any label, split, or metric computation.
This is the schema-level enforcement of the deliberately-designed test
that feeds the validator a lying executor (`docs/MASTER_RECORD_CONTENT.md`
§20).

## 9. Memory records

**Rule**: a `MemoryRecord` is only written after its own episode's
`ValidationOutcome` exists (`LearningManager` is the sole write path,
post-validation only). A dataset record must never expose a
`memory_interaction.memory_id_written` value whose `recorded_at` precedes
its own episode's `validation.validation_time` — any such record is a
generation-time defect, not a valid entry.

## 10. Future events

**Rule**: no field anywhere in the pre-decision portion of a record
(`observations`, `prediction`, `decision`) may be populated using any
event whose timestamp is later than `temporal.decision_time`. This
generalizes rule 1 to every field, not only the top-level snapshot, and is
the schema-level restatement of the design principle "No features from
future observations."

## 11. Derived features

**Rule**: every derived feature (e.g. `rss_ratio_env_normalized`) must
declare, in its `provenance.transformation_version`, the exact function
version that computed it, and that function must itself only consume
fields already validated against rules 1 and 10. A derived feature
computed from a mix of pre- and post-decision raw fields is itself a
leakage violation even if its own timestamp field is set correctly —
the schema requires `PHASE5_1_FIELD_LINEAGE.json` to list every input
field a derived feature consumed, so this can be checked mechanically.

## 12. Environment configuration

**Rule**: `workload.runtime_config` (e.g. `timeout_seconds`) is legitimate
pre-decision information — it is configured before the run starts, not
observed during it — and may be used as a feature. However, a value drawn
from `held_out`/`robustness` environment configuration must never be used
to *retrain* a model fit on `development` (rule 4); it may only be used as
a zero-shot evaluation input.

## 13. Train/calibration/test splits

**Rule**: see `PHASE5_1_SPLIT_POLICY.md` in full. Summarized: disjoint
`workload_id` groups and disjoint seed blocks across `train` /
`calibration_validation` / `test`; `calibrate_threshold` never receives
test rows; no threshold or model is ever refit after seeing a test-split
result (per `docs/MASTER_RECORD_CONTENT.md` §25's stated, audited
discipline, which post-P5 remediation Step 7's calibration-leakage audit
independently re-confirmed by direct code reading).

## 14. Cross-generation leakage (not named in the brief, added because the
evidence requires it)

**Rule**: Generation 1/2 (V1) evidence must never be merged with
Generation 3 evidence in any split, feature, or label — they are different
data-generating processes (trace replay vs. live subprocess execution).
This is not a "leakage" vector in the classical predictive sense, but
merging them would silently violate provenance-first and
do-not-mix-evidence-classes simultaneously, so it is stated here as an
explicit, additional leakage-adjacent rule.
